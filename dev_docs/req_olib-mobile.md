# 需求：无线传书自动开启 + 收书提示（来自 olib-mobile）

> 提出方：olib-mobile（`D:\SoftwareData\public\olib\olib-mobile`）
> 日期：2026-11-11
> 状态：已实现（桌面端分支 `feat/lan-auto-start-and-home-shortcuts`，2026-11-11），待发版后补版本号
>
> 桌面端答复：
>
> - 需求 1 按「上次开着就自动开」实现，配置 `lan_auto_start` + `lan_port`（端口沿用上次，不变）；书架「传书中」按钮靠 3 秒轮询，自动开启也能显示。
> - 需求 2 事件名与 payload 同本文件；连续到达合并提示，带「打开文件夹」；书单到达后收藏页自动刷新。
> - 待确认项：书架直接扫描 `download_folder`，手机发来的书**会**出现在书架，无需入库。
> - 顺带：`/api/upload` 不再限制格式和大小（docx、图片、压缩包等任意文件均可，也不再有 500 MB 上限 / 413），仅保留文件名路径穿越校验（400）。手机端若有本地的格式或大小预检，可一并放开。

## 背景

olib-mobile 新增了「电脑联动」页（首页快捷功能进入，分支 `feat/desktop-link-hub`）：

- 手机扫码配对一次后**记住这台电脑**（保存 `http://IP:8765`），之后打开页面先调 `GET /api/info`
  免认证探测，在线就直接取书 / 发书，不再扫码。
- 支持从手机已下载列表**多选批量发书**（逐本 `POST /api/upload`）。
- 下载页、书架导入、书单分享里原有的「发送到电脑 / 从电脑导入」也都改为优先用记住的电脑。

手机端只用了现有接口（`/api/info`、`/api/files`、`/download/{filename}`、`/api/upload`、`/api/booklist`），
**不改桌面端也能工作**。但桌面端有两处体验缺口，让「配对一次、之后免操作」打了折扣。

## 需求 1（推荐）：记住无线传书开关，启动时自动开启

### 现状

- 无线传书只能在书架页点「无线传书」→ 弹窗里手动开启（`WirelessTransfer.tsx` → `start_lan_server`）。
- 电脑端每次重启后服务都是关闭的。

### 问题

手机已经记住了电脑，但只要用户忘了在电脑上点开无线传书，手机「电脑联动」页就显示「暂时连不上电脑」，
用户得回到电脑前操作。记住配对的价值被这一步抵消了。

### 期望

- 配置新增一项，如 `lan_auto_start: bool`（默认 `false`，不改变现有用户行为）。
- 用户在电脑上**手动开启**无线传书时记为 `true`，**手动关闭**时记为 `false`。也就是「上次是开着的，下次启动就自动开」，不需要额外的设置项。
  如果你们更倾向于做成设置页里的显式开关，也可以。
- 应用启动时，若 `lan_auto_start == true`，按上次的端口（默认 8765）后台启动服务；
  启动失败（例如端口被占用）只记日志并保持关闭，不弹窗打扰用户。
- 书架页「无线传书」按钮的「传书中」状态，要能反映自动开启的情况（现在 `BookshelfPage` 用 `getLanStatus()` 读状态，应该已经满足，请顺带确认一下）。

### 注意

- 端口尽量保持稳定：手机记住的是 `IP:端口`，端口一变，手机就要重新扫码。
- 安全面不变：服务本来就监听 `0.0.0.0`、无认证（见 `lan-server.md`）。自动开启只是让这个状态持续得更久。
  如果担心公共 Wi-Fi 场景，可以在开启时提示一次「仅在可信网络使用」，具体由你们决定。

## 需求 2：收到手机发来的书 / 书单时，在电脑上提示

### 现状

- `receive_upload` 落盘后只有 `log::info!("📥 LAN upload received: ...")`，界面没有任何反馈。
- `/api/booklist` 导入后同样只有日志。

### 问题

手机端一次能批量发好几本书，但电脑上看不出书到了没有、放在哪里，用户只能去文件夹里翻。

### 期望

- 上传成功后向前端 emit 一个事件（如 `lan://file-received`，payload `{ name, size }`）；
  书单导入后 emit `lan://booklist-received`（payload `{ imported, skipped }`）。
- 前端收到后：
  - 弹一个轻提示（toast），例如「收到来自手机的《xxx》」。批量连续到达时合并成「收到 3 本书」，避免连续刷屏。
  - 如果当前在书架页，刷新列表，让新书立刻出现。
  - 可选：提示里带「打开所在文件夹」。
- 应用最小化或在后台时，可以考虑走系统通知。不是必须的。

### 待桌面端确认

- 上传的文件落在 `download_folder` 后，**书架页是否会显示它**？书架如果是基于数据库记录、而不是扫描目录，
  那手机发来的书可能不会出现在书架上，这个需要你们确认，必要时补上入库逻辑。

## 不需要改的

- 接口契约不变，手机端不依赖上面两项中的任何一项，两边可以分别发版。
- 无需恢复 token 认证。手机端保留了 token 字段和 401 处理，日后恢复认证时只改桌面端即可。

## 期望产物

1. 需求 1、2 的实现，以及 `dev_docs/lan-server.md` 的同步更新（自动开启的配置项、新增事件）。
2. 完成后在本文件「状态」处标注版本号，olib-mobile 侧会据此调整「暂时连不上」的提示文案
   （例如不再需要提醒用户去电脑上打开无线传书）。

# 需求：微信读书扫码中转（来自 olib-mobile）

> 提出方：olib-mobile（`D:\SoftwareData\public\olib\olib-mobile`）
> 日期：2026-11-25
> 状态：**代码已由 olib-mobile 侧代为实现，待桌面端审查**。桌面端分支 `feat/weread-qr-relay`（提交 `db8b50c`，基于 master，未合并、未推送）；手机端同名分支（提交 `ab46e9a`）。审查时可整体保留、改写或回退，手机端不受影响（见「兼容」）。
>
> 说明：按约定跨项目改动应只写需求、由桌面端自行实现。本次手机端在方案确认后直接改了桌面端代码，事后补此文档，供审查与留档。

## 背景

手机端的微信读书连接走微信移动接口扫码登录，**微信要求用「扫一扫」摄像头识别二维码**：

- 同一台手机打开确认链接或从相册识别都无法完成登录（真机已确认，见 olib-mobile `dev_docs/weread-home-engagement.md`）。
- 现状只能「发送到另一台设备」再扫；用户手边没有第二块屏幕时就连不上。

手机已配对的电脑正好可以充当这块第二屏。

## 方案选择

| 方案                                                                   | 结论                                                                                                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 电脑把自己的微信读书凭据（`weread_session.json`）下发给手机复用        | **否决**：LAN 服务无鉴权、明文 HTTP，凭据会暴露给同网络任何人；两端共用同一 `refreshToken` / `deviceId`，一端刷新可能使另一端失效，互相顶号 |
| **手机发起自己的扫码登录，把二维码推到电脑显示**，用手机微信扫电脑屏幕 | **采用**：凭据不经过 LAN；手机拿到独立会话；电脑只负责显示一张图                                                                            |

## 需求

### 1. 接口

| 端点                        | 请求体                              | 行为                                                      | 响应                                             |
| --------------------------- | ----------------------------------- | --------------------------------------------------------- | ------------------------------------------------ |
| `POST /api/weread-qr`       | `{ "url": string, "code": string }` | 校验通过后生成二维码图片，通知前端弹窗显示二维码 + 识别码 | `200 { ok: true }`；校验失败 `400 { detail }`    |
| `POST /api/weread-qr/close` | `{ "code": string }`                | 关闭该识别码对应的弹窗（识别码不匹配当前弹窗时忽略）      | `200 { ok: true }`；`code` 非法 `400 { detail }` |

- `GET /api/info` 的 `capabilities` 增加 `"weread_qr"`。手机端据此判断是否支持；不支持时提示「电脑端版本较旧」。
- `400 { detail }` 沿用现有约定，手机端会展示 `detail`。

### 2. 防假码（必须）

LAN 服务无鉴权（2026-07-16 取消 token），而这个接口会在电脑上弹出**微信授权码**。同网络的人可以推来**自己发起的**登录码，用户一旦扫了，就把自己的微信读书账号授权给了对方。

用户决定**不恢复 token**，改为两条防线：

1. **只接受微信官方授权确认链接**：`https` + 主机正好是 `open.weixin.qq.com` + 路径 `/connect/confirm` + 带非空 `uuid` 参数，其余内容一律 400、不显示。主机名必须完全相等（`open.weixin.qq.com.evil.com` 之类要拒绝）。
2. **识别码核对**：手机生成 4 位数字识别码（`Random.secure`），手机与电脑弹窗**同时醒目显示**。弹窗须提示「核对与手机上显示的一致；不一致或不是你发起的，请直接关闭，不要扫码」。`code` 必须恰好 4 位 ASCII 数字。

不采用「按来源 IP 区分 / 提示」：用户无法判断哪个 IP 是自己的手机。

### 3. 前端

- 全局挂载（与 `LanReceiveNotifier` 同级），不依赖当前页面。
- 收到显示事件：弹窗展示二维码（≥ 200px，手机摄像头可识别）、识别码（大号、等宽数字）、核对提示；新请求覆盖旧弹窗。
- 收到同识别码的关闭事件、点遮罩、Esc 或关闭按钮时收起。
- 不需要倒计时：微信二维码 5 分钟过期由手机端处理，过期或重新生成时手机会先发关闭请求。

### 4. 日志与隐私

- 可记录「显示了二维码（识别码 xxxx）」；**不记录二维码 URL 中的 `uuid`**。
- 电脑端不保存、不转发任何微信读书凭据。

## 手机端行为（`ab46e9a`）

- 微信读书页「生成二维码」后，若已配对的电脑在线，显示「在电脑上显示二维码」。
- 点按：探测 `/api/info` → 检查 `weread_qr` → 生成识别码 → `POST /api/weread-qr` → 手机上显示同一识别码与核对提示。
- 登录成功 / 失败 / 重新生成 / 断开 / 离开页面时 `POST /api/weread-qr/close`（失败只记日志）。

## 兼容

- 桌面端回退或不合并：手机端看不到 `weread_qr` 能力，只提示「请先更新电脑端 Olib」，原有「发送到另一台设备」不受影响。
- 不影响现有传书、书单、OPDS 接口，也不恢复 token。

## 验收

1. 手机生成二维码 → 点「在电脑上显示」→ 电脑弹窗；两端识别码一致。
2. 手机微信扫电脑屏幕 → 手机连接成功 → 电脑弹窗自动关闭。
3. 手机重新生成二维码 / 返回上一页 → 电脑旧弹窗关闭。
4. 用 curl 推非微信链接或非 4 位识别码 → 400，电脑不弹窗。
5. 完成后在本节「状态」处标注发版版本号。
